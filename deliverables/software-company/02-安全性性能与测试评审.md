# A. 安全性评审

## A.1 命令注入 / 参数注入 —— 结论：**未发现可利用的 shell 注入** ✅

这是本次最优先排查项，结论是**好消息**，但过程与细节值得写清楚。

### 【结论】三处外部进程调用全部使用 `ProcessBuilder(List<String>)`，无 shell 中介，无 `Runtime.exec(String)`，无 `cmd /c`

- 【证据】`MavenCompileService.java:141-145`
  ```java
  List<String> cmd = new ArrayList<>(Arrays.asList(mavenCommand(), "-B", "-DskipTests", goal));
  ...
  ProcessBuilder pb = new ProcessBuilder(cmd).directory(projectDir.toFile()).redirectErrorStream(true);
  ```
- 【证据】`GitCloneService.java:515-532`
  ```java
  List<String> cmd = new ArrayList<>(); cmd.add("git"); ... ProcessBuilder pb = new ProcessBuilder(cmd);
  ```
- 【证据】`GitCloneService.java:697`（`reg query`）、`GitRefService.java:335-342`（本地 git）
- 【证据】`JavacCompileService.java:76-102` —— **根本不起进程**，走 JDK 内建 `javax.tools.JavaCompiler` API
- 【证据】全仓 grep 无 `Runtime.getRuntime().exec`、`ProcessBuilder(String)`、`cmd /c`、`/bin/sh -c`
- 【影响】`& | > < ^ ; $()` 等 shell 元字符在用户可控字段中**不具威胁**，因为整条命令从未交给 shell 解析
- 【建议】保持现状；在 `MavenCompileService`/`GitCloneService` 类注释里写明"**禁止改回单字符串 exec**"，避免后人优化时踩坑

### 【问题】`javac` 存在**注解处理器自动发现**导致的进程内代码执行路径 🟠

- 【证据】`JavacCompileService.java:87-102`：`-classpath` 由被分析仓库内收集的 `*.jar` 拼成，且未加 `-proc:none` / `-processorpath`
  ```java
  String cp = libJars.stream().map(Path::toString).collect(Collectors.joining(File.pathSeparator));
  args.add("-classpath"); args.add(cp);
  ...
  Boolean ok = compiler.getTask(pw, fm, diagnostics, args, null,
          fm.getJavaFileObjects(...)).call();
  ```
- 【影响】<推断> javac 在未显式指定 `-processor` / `-proc:none` 时，会在 classpath 上按 `META-INF/services/javax.annotation.processing.Processor` 自动发现并**执行**注解处理器。若被分析仓库（或 Git 仓库）里带一个投毒 jar，处理器代码会在**本工具自己的 JVM 内执行** → 任意代码执行。
- 【建议】classpath 拼接后追加 `-proc:none`（本工具只读字节码，不需要注解处理）；若将来需要支持，再显式指定 `-processorpath` 白名单。

### 【问题】mvn 的 `-Dmaven.repo.local` 由可写环境变量 / 系统属性注入 🟡

- 【证据】`MavenCompileService.java:136-139, 185-191`
  ```java
  String repoOverride = System.getProperty("callgraph.maven.repo");  // 或 env CALLGRAPH_M2_REPO
  ... cmd.add(2, "-Dmaven.repo.local=" + repoOverride.trim());
  ```
- 【影响】单个 argv 元素，无法逃逸成第二个参数（无 shell）→ **不可利用**；但若该值含空格/换行，会让 mvn 解析出非预期仓库路径，导致 `clearPartialArtifacts()`（`:88-112`）在**错误目录**下按"10 分钟内的 `.part`/`.part.lock`"批量删文件。
- 【建议】对 `mavenRepoPath()` 返回值做白名单校验（必须是已存在目录、不含空白与控制字符），再拼进 argv。

## A.2 对不可信仓库执行 `mvn compile` —— 🔴 本项目最实质的高危面

### 【问题】克隆任意用户指定仓库后立即执行 `mvn compile`，Maven 生命周期会执行 pom.xml 中绑定的任意插件代码

- 【证据】`GitPrepareService.java:154-165`
  ```java
  if (located.needMaven) {
      job.status = "COMPILING";
      MavenCompileService.CompileResult r = mavenCompileService.compile(compileDir, job.compileLog::add);
  ```
- 【证据】`MavenCompileService.java:132-134` 执行的是 `mvn -B -DskipTests compile`（`compileClean` 为 `mvn clean compile`），`compile` 阶段覆盖 validate→…→compile 全生命周期
- 【证据】同步入口同样存在：`AnalysisController.java:187-195` —— `/api/ensure-compile`、`/api/scan/entries` 会对**任意传入路径**执行 `mvn compile` / `mvn clean compile`
  ```java
  if (Files.exists(root.resolve("pom.xml"))) {
      MavenCompileService.CompileResult r = force
              ? mavenCompileService.compileClean(root)
              : mavenCompileService.compile(root);
  ```
- 【证据】真实使用痕迹：实测 `GET /api/projects` 返回中已存在 `https://github.com/spark-young/kkFileView.git`、`https://github.com/spark-young/spark-live-classroom.git` 两个外部 GitHub 项目 `<已验证>` —— 说明"导入外部仓库并编译"是**正在发生的真实用法**，不是理论路径
- 【影响】Maven 的 pom.xml 可以绑定 `exec-maven-plugin` / `maven-antrun-plugin` / 任意第三方插件到 `validate`/`compile` 阶段。也就是说：**谁能让你导入一个仓库，谁就能在本机以你的用户身份执行任意命令**。这是"mvn 编译不可信工程"的经典结论，与是否使用 shell 无关。
- 【缓解现状】默认只绑 127.0.0.1（`application.yml:5`），攻击者需先具备本机代码执行能力或诱导用户访问恶意页面（DNS rebinding）
- 【建议】
  1. 首次导入外部仓库时给出**显著风险提示**并要求二次确认；
  2. 增加"编译沙箱"选项：以低权限用户 / 容器 / `mvn -o` 离线模式运行；至少设置 `MAVEN_OPTS` 与 `~/.m2/settings.xml` 隔离；
  3. 对 Git 仓库来源做域名白名单（内网 GitLab 域名），白名单外强制二次确认；
  4. 至少记录"某仓库触发了 mvn 编译"的审计日志（当前 `logging.level.root: info` 无任何访问审计）。

## A.3 Git URL 不校验 —— SSRF + 本地命令执行 🔴

### 【问题】`repoUrl` 全链路无协议白名单、无主机白名单，直接作为 argv 传给 `git`

- 【证据】`GitCloneService.java:61-65`（`ls-remote`）、`109-116`（`rev-parse` + `ls-remote`）、`136-166`（`fetch`/`checkout`）、`427-428`（`clone`）
  ```java
  String out = git(new String[]{"ls-remote", "--symref", "--heads", "--tags", authed}, repoUrl);
  ```
- 【证据】`sanitizeUrl()`（`GitCloneService.java:771-805`）**只做"去包装字符"**（反引号/引号/括号/末尾冒号斜杠），**不做协议或主机校验**
- 【证据】`GitPrepareService.prepare()`（`:87-90`）对 `repoUrl` 唯一的校验是"非空"
  ```java
  if (req == null || req.getRepoUrl() == null || req.getRepoUrl().trim().isEmpty()) {
      throw new AnalysisException(HttpStatus.BAD_REQUEST, "仓库地址不能为空");
  }
  ```
- 【影响】
  1. **SSRF**：`http://169.254.169.254/...`、`http://10.x.x.x:8080/...` 等内网地址可被 `git ls-remote` 探测（`proxyFor()` 的"内网直连"逻辑 `:591-607` 恰恰保证内网地址不走代理，探测更顺畅）。
  2. **本地仓库读取**：`file:///C:/...` 可克隆本机任意 git 仓库（测试自身就用这种 URL）。
  3. **任意命令执行**：git 支持 `ext::` remote helper（`git ls-remote "ext::<命令>"` 会执行该命令）。URL 未经协议白名单过滤即进入 argv → 这是**命令执行**，且绕开了 A.1 的"无 shell"结论（因为 git 自己就是执行者）。<推断：未在本环境实测 `ext::`，因本机 git 环境异常（§C.1），但协议未过滤是代码事实>
- 【建议】在 `GitCloneService` 入口统一加协议/主机校验：
  ```java
  private static void assertAllowedUrl(String url) {
      String u = url == null ? "" : url.trim().toLowerCase();
      if (!(u.startsWith("http://") || u.startsWith("https://") || u.startsWith("ssh://") || u.startsWith("git@"))) {
          throw new IllegalArgumentException("不支持的仓库协议（仅允许 http/https/ssh/git@）");
      }
      // 内网场景再叠加域名白名单 / 或禁止 169.254.169.254 等链路本地地址
  }
  ```
  并在 `GitPrepareService.prepare()`、`GitCloneService.listRefs/checkRemoteUpdate/switchRef/ensureLocal` 五处入口调用。

### 【问题】Git 参数注入（argument injection）敞口 🟡

- 【证据】`GitCloneService.java:161` —— `git checkout <target>` 中 `target` 未加前缀，若以 `-` 开头会被 git 当作选项
  ```java
  git(new String[]{"-C", dir, "checkout", target}, repoUrl);
  ```
  （同函数 `:156` 的 `tags/" + target`、`switchRef` 其余调用、`pullWithRetry:389` 的 `safeBranch(branch)` 都存在同类形态）
- 【影响】<推断> 可诱导 git 走非预期分支/选项（`--orphan`、`-B`、`--conflict=` 等），目前未找到可 RCE 的 git checkout/fetch 选项组合；但这是典型的" باید 加 `--`"防御缺失
- 【建议】
  1. 所有 refspec / 分支名参数前加 `--` 分隔符：`git checkout -- <target>`；
  2. 分支名做正则白名单：`[A-Za-z0-9._\-/]+` 且不以 `-` 开头。

### 【问题】全局关闭 TLS / SSH 主机校验 🟠

- 【证据】`GitCloneService.java:526-530`
  ```java
  pb.environment().put("GIT_ASKPASS", "echo");
  pb.environment().put("GIT_SSH_COMMAND",
          "ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o ConnectTimeout=15");
  pb.environment().put("GIT_SSL_NO_VERIFY", "1");
  ```
- 【证据】`GitCloneService.java:332-334`（JGit 侧同样 `StrictHostKeyChecking=no` + `UserKnownHostsFile=/dev/null`）
- 【影响】所有 git 操作的 TLS 证书与 SSH 主机指纹校验被完全关闭 → 内网 MITM 可直接窃取出站 Git Token，或投喂恶意代码供后续 `mvn compile` 执行（与 A.2 形成攻击链）
- 【建议】默认开启校验；仅在用户明确勾选"忽略证书校验（内网自签名）"时才设置，并对该操作记 warn 日志。

### 【问题】git 进程**无超时**，单个请求可永久挂起 🟠

- 【证据】`GitCloneService.java:556` —— `int code = p.waitFor();`（无超时）
- 【证据】`GitRefService.java:347` —— 同样是 `p.waitFor()`
- 【证据】对比：`MavenCompileService.java:165` 有 15 分钟超时（`p.waitFor(timeout, unit)`）
- 【影响】配合单线程 executor（`GitPrepareService.java:34`、`GitRefService.java:47`、`EntryScanService.java:52`），一次"卡住的 git"会让**整个 Git 导入 / 分支切换功能永久不可用**，重启才能恢复；`pullWithRetry`（`:386-405`）还会重试 3 次、每次卡死
- 【建议】改用 `p.waitFor(n, TimeUnit.MINUTES)`，超时 `destroyForcibly()`。

### 【问题】缓存文件名未做任何净化，**可读取项目外任意路径文件** 🟠 <已验证>

- 【证据】`AnalysisCacheService.java:255-267`

- 【证据】`fileName` 的三个外部入口均为用户可控：

- 【证据】**实测结果** `<已验证>`（对已存在的 LOCAL 项目 `91bcd1b6-...`，目标文件位于另一个盘符）：
  ```
  GET /api/projects/91bcd1b6-96b0-44a7-865b-1a0de1cf41a1/cache/load
      ?fileName=C:\Users\lenovo\AppData\Local\Temp\qa-perf\app.jar.callgraph\cache\AnalysisService#analyze_448d9314.json
  → HTTP 200，3,519,433 bytes（完整返回，路径完全在项目之外）

  ```
  Java `Path.resolve(绝对值)` 会直接返回该绝对路径，因此连 `..` 都不需要，跨盘符也能读。
- 【影响】
  - 任意文件**存在性探测**（200 / 404 可区分）；
  - 任意**合法 JSON** 文件可被反序列化并以 `AnalysisResult` 字段形式回吐（`mapper.configure(FAIL_ON_UNKNOWN_PROPERTIES, false)`，见 `:43`，未知字段被丢弃）→ 部分内容泄漏；
  - 反序列化大文件（无体积限制：`loadByFileName` 无 `SINGLE_CACHE_MAX_BYTES` 之类的保护，只有 `loadSingle` 有 30MB 限制）→ 内存放大 DoS。
- 【建议】
  ```java
  public Optional<AnalysisResult> loadByFileName(String projectPath, String fileName) {
      if (fileName == null || fileName.contains("\0")) return Optional.empty();
      Path dir = cacheDir(projectPath).normalize().toAbsolutePath();
      Path file = dir.resolve(fileName).normalize().toAbsolutePath();
      if (!file.startsWith(dir)) {                       // 关键：越界直接拒绝
          log.warn("[缓存] 拒绝越界文件名: {}", fileName);
          return Optional.empty();
      }
      if (!file.getFileName().toString().endsWith(".json")) return Optional.empty();
      if (!Files.isRegularFile(file)) return Optional.empty();
      return loadCached(file, fileName);
  }
  ```

# B. 性能评审

> 说明：应用由 IntelliJ 已运行在 `127.0.0.1:8080`（PID 25852，JDK 11.0.8，Windows 10）。
> 测试对象：本工程自身的 fat jar（37.9 MB，`BOOT-INF/classes` 124 个类 + 44 个依赖 jar），复制到 `%TEMP%\qa-perf\` 下分析，**不污染仓库**（`.gitignore` 已含 `.callgraph/`）。

## B.1 实测数据

| 场景 | 实测结果 |
|---|---|
| `GET /api/projects`（冷，5 个项目，触发磁盘状态检测） | **580 ms** |

| `GET /api/project/info`（fat jar，需解压 37.9 MB） | **1,686 ms** |
| `POST /api/analyze`（**注册表冷** + 缓存未命中） | **11,730 ms**，响应 **3,519,435 B（3.35 MB）**，内部 `durationMs=7041` |
| `POST /api/analyze`（注册表热 + 缓存未命中，另一方法） | **381 ms**，响应 125,655 B，内部 `durationMs=9` |
| `POST /api/analyze`（**磁盘缓存命中**） | **256 ms** |

**耗时构成拆解（关键）**：
- 注册表冷 = 11.7 s，注册表热 = 0.38 s → **首次/切项目的 ~7 s（内部 durationMs 7041ms）几乎全部是"解压 fat jar + ASM 索引 45 个 jar"**；真正的图构建只有 **9 ms**。
- 冷路径 11.7 s 中约 **4.7 s 是 3.5 MB 响应的序列化 + 传输**（11,730 − 7,041）。
- 结论：**性能瓶颈不在算法，在"注册表构建"和"响应/缓存体积"**。

## B.2 问题清单

### 【问题】单次分析响应体积失控：3.35 MB / 一个入口 🟠

- 【证据】实测 3,519,435 B；内容为 `methodFrequency` = **4,272 条**，每条带完整 `callers` 列表
- 【证据】`AnalysisService.java:52-54`
  ```java

  private static final int CALLER_CAPTURE_LIMIT = Integer.MAX_VALUE;   // 完整采集
  ```
  → `topFrequency()`（`:546-556`）把**全部** 4272 个方法 + 调用方明细塞进 JSON
- 【影响】
  - 前端 `renderFreqList()`（`app.js:2590-2646`）把整个列表一次性 `innerHTML` 拼装，**无分页、无虚拟滚动** → 4272 个 DOM 节点；大项目（数万方法）必然卡死/白屏；

- 【建议】
  1. 后端 `methodFrequency` 默认 Top N（如 300）并支持分页参数；`callers` 改为按需接口（点展开时再取）；
  2. 缓存写入关闭 `INDENT_OUTPUT`（`AnalysisCacheService.java:42`），实测可省 30%+ 体积；
  3. 前端 `freqList` 改虚拟滚动或分段渲染。

### 【问题】默认 `maxDepth=20` 就已截断，且结果里 94% 是依赖噪声 🟠

- 【证据】实测 `stats: {"totalNodes":4273,"projectMethods":224,"dependencyMethods":4010,"externalMethods":39,"truncated":true}`
- 【影响】
  - `truncated=true` 意味着**默认参数下调用链就是残缺的**，但响应里没有任何显著提示（前端是否展示需确认）；
  - 4273 个节点里只有 **224 个（5.2%）是项目自身方法**，其余是 Spring/JDK 依赖 → 用户想看的"交易链路"被淹没，同时付出 20 倍的内存与体积代价。
- 【建议】
  1. 默认 `maxDepth` 降到 8~12，并在 UI 上把 `truncated` 做成醒目告警；

- 【证据】`AnalysisService.java:56-57, 404-448`
  ```java

  private synchronized CacheSlot obtainRegistry(...) {    // 全局锁
      ... System.currentTimeMillis() - current.ts < CACHE_TTL_MS /* 5 分钟 */
  ```

- 【影响】
  - A/B 两个项目交替操作 → 每次都丢弃重建（7 s）；

- 【证据】`AnalysisCacheService.java:155-170`

  ```java
      java.util.TreeSet<String> keys = new java.util.TreeSet<>();
  ```

### 【问题】遍历效率：`Files.walk` 深度过大 + 重复 IO 🟡

- 【证据】深度 100：`ProjectsController.java:285`、`AnalysisController.java:199`、`GitPrepareService.java:326`、`GitRefService.java:270`
- 【证据】深度 50：`ProjectsController.java:239, 251`、`AnalysisController.java:249`

- 【证据】`ProjectRegistry.list()`（`:36-48`）每次调用都**重读并反序列化整个 projects.json**；`getByPath`/`get` 内部再调 `list()` → `GitPrepareService.java:172` 的一次注册可能触发多次全量读盘（N+1 式）

### 失败 1️⃣2️⃣3️⃣：`GitPrepareServiceTest` 的 3 个 DONE/FAILED 断言

**先说清根因（交接文档的说法成立，我做了静态确认）**：

- 【证据】生产调用点用的是**两参重载**：
  `GitPrepareService.java:158` → `mavenCompileService.compile(compileDir, job.compileLog::add);`
- 【证据】两参重载存在：`MavenCompileService.java:34`
  ```java
  public CompileResult compile(Path projectDir, Consumer<String> onLine) { ... }
  ```
- 【证据】测试桩只覆写了**一参**：`GitPrepareServiceTest.java:23-32`
  ```java
  static class StubCompileService extends MavenCompileService {
      @Override public CompileResult compile(Path projectDir) { ... }   // ← 只有这个
  }
  ```
  Java 重载在**编译期**按调用点签名解析，调用点是两参 → 直接走父类真实实现 → 真去跑 mvn → 夹具 pom 是 `"<project/>"`（`:53`）→ mvn 报 `'modelVersion' is missing` → 与交接文档描述完全吻合 ✅
- 【证据】另两个"新增"失败（`test_prepare_plainJavaSource_compiledByJavac:227`、`test_prepare_plainJava_javacFailure:247`）同因：它们卡在**克隆阶段**（本机 git 故障），修好 git 环境后，`plainJava` 用例会走 `javacCompileService`（桩是完整的 ✅），但 `stub.compiledDir` 仍不会被赋值 —— 这两个用例本身不依赖 mvn 桩。

**修复补丁（只需改测试的桩类）**：
```java
// GitPrepareServiceTest.java:23-32
static class StubCompileService extends MavenCompileService {
    Path compiledDir;
    boolean fail;

    @Override
    public CompileResult compile(Path projectDir) {
        this.compiledDir = projectDir;
        return fail ? CompileResult.failure("模拟编译失败") : CompileResult.success();
    }

    /** 补齐重载：GitPrepareService 实际调用的是 compile(Path, Consumer<String>)（GitPrepareService.java:158），
     *  不覆写会导致桩被绕过、真的去跑 mvn（夹具 pom 只有 <project/>，必然报 modelVersion 缺失）。 */
    @Override
    public CompileResult compile(Path projectDir, java.util.function.Consumer<String> onLine) {
        return compile(projectDir);
    }
}
```
【成本】**约 2 分钟**，纯测试文件改动、4 行。

**另一半必要条件：修好本机 git 环境**（否则这 3 个 + 另外 2 个会继续卡在克隆阶段）：
