## A. 代码架构

### A-1【P0】`AnalysisService` 单例共享可变状态，`/api/method-callers` 是必然报错的死接口

**【问题】** `AnalysisService` 用两个 `volatile` 实例字段缓存"最近一次分析结果"，靠 `projectPath` 字符串比对判断是否可复用。`/api/method-callers` 调用时传的是 `null`。

**【证据】**
- `AnalysisService.java:59-61` 定义 `lastResult` / `lastResultProjectPath`
- `AnalysisService.java:352-358` `getLastResult(String projectPath)`：`if (lastResult != null && projectPath != null && projectPath.equals(...))` —— **`projectPath` 为 `null` 时恒返回 `null`**
- `AnalysisController.java:347` `AnalysisResult result = analysisService.getLastResult(null);`
- `AnalysisController.java:348-350` 紧接着 `if (result == null) throw new AnalysisException(BAD_REQUEST, "请先执行一次分析");`

**【影响】** `/api/method-callers` 这个 CSV 导出接口**无论何时调用都必然返回 400**，即使刚分析完。同时 `lastResult` 是**无隔离的跨请求共享状态**：两个人/两个项目并发使用会互相串数据（后一个请求覆盖前一个，Excel 导出可能导出到别人的结果）。

**【建议】**
1. 短期止血：`AnalysisController.java:347` 改为传入 `req` 里带的 `projectPath`（为该接口增加 `projectPath` 查询参数），或直接用 `cacheService.loadByFileName`。
2. 根因修复：把 `lastResult` 这类"会话态"从单例 Service 里拿掉 —— 新建 `AnalysisResultStore`，key 用 `projectId + jobId`，带 TTL 与容量上限；或让 Excel 导出一律走 `cacheService.loadByFileName(...)`（该能力已经存在，`AnalysisController.java:280` 就在用），彻底删掉 `lastResult` / `rememberLastResult`。
3. 删除 `AnalysisService.java:361-364` `rememberLastResult`（仅 `BatchAnalyzeService` 场景需要，可改为显式传参）。

**【问题】** `AnalysisController` 里有 80 行的"探测项目类型 → 决定 Maven 还是 javac → 决定是否需要 clean compile → 找已有编译产物"的编排逻辑，这属于应用服务职责。Controller 因此直接依赖 `MavenCompileService` + `JavacCompileService` 两个重组件。

**【建议】** 抽出 `CompileOrchestrationService`（放 `service/`），把 `compileIfNeeded` / `findExistingArtifacts` / `hasClassFiles` 整体搬过去，并把"编译产物候选目录"抽成常量（如 `ProjectLayout` 或新 `BuildLayouts`）。`AnalysisController` 只保留一行调用。

### A-3【P1】`GlobalExceptionHandler` 覆盖度不足，HTTP 语义错误

**【问题】** 全局异常处理器只处理 3 类：业务异常、客户端断开、兜底 `Exception`。Spring MVC 的常见 4xx 场景（请求体 JSON 非法、缺必填参数、参数类型不匹配、方法不支持）全部落到兜底分支，**返回 500 而不是 400**。

**【证据】**
- `GlobalExceptionHandler.java:21-47` 仅 `AnalysisException` / `ClientAbortException` / `Exception`
- `GlobalExceptionHandler.java:38` 兜底分支 `ResponseEntity.status(500)`
- 全库搜索 `@Valid|@Validated|@NotNull` → **0 命中**（`<已验证>`）：完全没有声明式校验，所有入参校验靠手写 if + 手抛异常
- 实测佐证（`<已验证>`，来自 `target/surefire-reports`）：`AnalysisControllerTest.java:197` `test_scanEntries_badPath_rejected` 失败 —— `Status expected:<400> but was:<500>`

**【影响】** 客户端拿到 500 会误判为服务端故障；错误码语义不统一；排查成本上升。另一个副作用：`GlobalExceptionHandler.java:40` 把 `e.getMessage()` 直接回给客户端，内部异常细节外泄。

**【建议】**
1. 在 `GlobalExceptionHandler` 增加 `@ExceptionHandler(HttpMessageNotReadableException.class)`、`MissingServletRequestParameterException`、`MethodArgumentTypeMismatchException`、`HttpRequestMethodNotSupportedException → 405`，均映射 400/405。
2. 兜底分支改为 `log.error` 完整堆栈 + 返回**不带 `e.getMessage()`** 的通用文案（如 `"内部错误，详见服务端日志"`），避免信息外泄。
3. 在 `AnalyzeRequest`、`ScanRequest` 上加 `@NotNull @NotBlank` + Controller 参数加 `@Valid`，把 `AnalysisService.validate()`（`AnalysisService.java:390-402`）的手写校验前移。

### A-4【P1】两个 Controller 共用同一个 base path `/api/projects`

**【问题】** `ProjectsController` 与 `EntryListController` 都声明 `@RequestMapping("/api/projects")`。

**【证据】** `ProjectsController.java:49` 与 `EntryListController.java:40`；两者方法级子路径不重叠（`/{id}/cache/*` vs `/{id}/entries/*`），因此**当前不会触发启动期 ambiguous mapping 冲突**（`<已验证>`：逐个方法路径比对无重复）。

**【影响】** 路由归属不清 —— 想知道 `/api/projects/{id}/xxx` 有哪些能力必须同时打开两个文件；后续任一方新增一个裸 `@GetMapping` 就会直接把应用搞成启动失败。

**【建议】** 二选一：(a) 把 `EntryListController` 的 base path 改为 `/api/projects`（保留）但把 `ProjectsController` 拆分，或 (b) 更省事：把 `EntryListController` 的映射改为 `/api/projects/{id}/entries` 类级路由（`@RequestMapping("/api/projects/{id}/entries")`），方法级去掉 `{id}`。至少要在两个类上加互相 @see 的注释。

### A-8【P2】命名语义冲突：`GraphMethod#getDisplay()` 返回的其实是 identifier

**【问题】** `MethodKey#getDisplay()` 返回短形式（如 `pay(String)`），`GraphMethod#getDisplay()` 返回的却是全限定标识（`com.foo.Bar#pay(String)`）。同名方法，语义完全不同。

**【证据】**

- `app.js:3541-3545`：`return s.replace(/[&<>"']/g, ...)` —— **无 null 保护**，转义单引号 `'` → `&#39;`
- `app.js:3925-3928`：`return String(s == null ? '' : s).replace(/[&<>"]/g, ...)` —— **有 null 保护，但不转义单引号**

JS 函数声明会提升且**后定义者覆盖先定义者**，因此实际生效的是 `3925` 版本（`<已验证>`：两者同为 4 空格缩进的顶层声明，属同一作用域）。

**【影响】**
1. `3541` 那份是**死代码**，读代码的人会以为单引号被转义了，实际没有。
2. 行为随"谁在后面"而变 —— 任何人调整代码顺序都会静默改变转义语义。
3. 全文件大量用 `innerHTML` 拼串（`app.js:385` `projectCardHtml`、`:3877` `renderEntryRow`、`:4812` `<option value="${m.name}" data-desc="${m.descriptor}">` 等），转义不一致是潜在的 HTML 注入面。**注**：`data-desc` 等属性用双引号包裹，仅单引号不足以外泄属性，故这里**不构成已确认漏洞**（`<推断>`，需 QA 复核）；但 `app.js:4812` 的 `${m.descriptor}` 未经 `escapeHtml` 直接插值，**如果 descriptor 含双引号就会破坏属性边界** —— 这一点请 QA 重点看。

**【建议】** 立即删除 `app.js:3541-3545`，全库统一用 `3925` 版本（null-safe 更重要），并把单引号补上：`replace(/[&<>"']/g, ...)`。同时把 `app.js:385/3877/4812` 等 innerHTML 插值点统一走 `escapeHtml`（属性值场景建议改用 `textContent` + DOM API，彻底免疫）。

### C-1【P0】分析结果缓存**永不失效**：`projectFingerprint()` 写了但从未被调用

**【问题】** `AnalysisCacheService` 实现了项目指纹计算（Git HEAD / pom 时间 / 最新 class 时间），但**缓存文件名刻意不包含指纹**，且指纹方法没有任何调用点。

**【证据】**（`<已验证>`）
- `AnalysisCacheService.java:399-434` `static String projectFingerprint(String projectPath)` —— 实现完整（`.git/HEAD` → `pom.xml` mtime → `build.gradle` mtime → `target/classes` 最新 class mtime）
- 全库搜索 `projectFingerprint` → **仅此 1 处定义，0 处调用**（`newestClassTime` 同理仅被它自己调用）
- `AnalysisCacheService.java:342-350` `cacheName()` 注释明写：`* hash 只由 入口 + 分析配置 决定，不含项目指纹 —— 同一入口重分析覆盖同名文件，不堆积旧版本`
- `AnalysisService.java:266-286` 缓存命中路径：`useCache && !multiEntry` 为真时直接 `cacheService.load(...)` 返回，**不做任何新鲜度校验**
- 唯一逃生阀：`AnalyzeRequest.skipCache`（`AnalyzeRequest.java:13`），前端在 `app.js:1281-1295` 手动传

**【影响】** 这是本次评审发现的**正确性最严重的问题**：
> 用户改了业务代码 → 重新编译 → 点"重新分析" → **拿到的还是旧代码的调用链**，且没有任何提示。

对一款"用来判断哪些交易受影响"的分析工具来说，这直接摧毁结论可信度。更糟的是它**不会报错**，用户会毫无察觉。`<推断>`：用户可能已经遇到过"结果不对"但归因于"分析不准"，实际是缓存。

补充两条次生风险：
- Git 指纹只取 HEAD 的 ref 值（`:409-415`），**不看工作区是否 dirty** —— 即使启用指纹，未提交的代码改动也不会触发失效。
- 非 Git 项目走 `pom.xml` mtime：改 `.java` 但不动 `pom.xml` → 指纹不变 → 同样失效不了。只有最后一条 `class:` 分支（最新 `.class` 时间）能真正反映代码变化，而它优先级最低。

**【建议】**（按成本递增）
1. **最低成本（推荐先做）**：让 `load()` 做**新鲜度校验**而非仅按名命中。在 `AnalysisCacheService.save()` 时把 `projectFingerprint(projectPath)` 写进 JSON 的 `meta` 字段；`load()` 时重算指纹比对，不一致则返回 `Optional.empty()` 并在日志/响应里标记"缓存已过期，已重新分析"。文件名规则不变（保留"不堆积旧版本"的初衷）。
2. 同时把 `projectFingerprint` 的优先级调整为：**最新 `.class` 文件时间 > pom/gradle mtime > Git HEAD**，因为只有前者能反映真实代码变化。Git 场景可改为 `HEAD + git status --porcelain 是否为空`。
3. UI 侧：分析结果上带一个"分析于 <时间> / 项目指纹 <hash>"标签，让用户能自己看出新旧。

### C-3【P1】`BatchAnalyzeService` 的 Job 永不清理（内存泄漏）

**【问题】** Job TTL 清理逻辑只清理"失败"的 Job，**成功的 Job 永远留在 `jobs` map 里**。

**【证据】**（`<已验证>`）
- `BatchAnalyzeService.java:286-293` `cleanupExpired()`：`if (j.doneAt == 0) return false;` —— `doneAt` 为 0 就跳过
- `BatchAnalyzeService.java:265-271` `fail()` **设置** `doneAt = System.currentTimeMillis()`
- `BatchAnalyzeService.java:211` 成功路径调用 `job.update(DONE, 100, ...)`，而 `update()`（`:253-263`）**不设置 `doneAt`**
- 清理只在 `startAsync()`（`:87`）被动触发 —— 不发起新任务就不清理

**【影响】** 所有成功完成的批量任务对象永久驻留。每个 `Job` 持有 `AnalyzeRequest`（含 `entries` 列表，批量场景可达数百条）。长驻运行、分析几十次后持续累积；且因清理只在新任务提交时触发，**失败任务的 5 分钟 TTL 也形同虚设**。

**【建议】**
1. 在 `Job.update()` 中，当 `state == DONE` 时同步设置 `doneAt`（或在 `:211` 后显式 `job.doneAt = System.currentTimeMillis()`）。
2. 加 `@Scheduled(fixedDelay = 5*60*1000)` 定时清理（需 `@EnableScheduling`），不要只依赖 `startAsync` 触发。
3. 同样问题需检查 `EntryScanService`（`:52` 同构）、`GitPrepareService`（`:34`）、`GitRefService`（`:47`）—— 三者都是 `newSingleThreadExecutor` + `ConcurrentHashMap<String, Job>` 的相同模式（`<推断>`，未逐个验证各家的 `doneAt` 赋值）。
4. 顺带：这 4 个 `ExecutorService` 均无 `@PreDestroy` 关闭钩子。线程是 daemon（`:59` `t.setDaemon(true)`）故不阻塞退出，但 Spring 上下文重建时会泄漏线程。建议统一加 `@PreDestroy public void shutdown() { executor.shutdownNow(); }`。

### C-4【P0】JGit 5.1.3 存在已知高危漏洞，且未做任何缓解

**【问题】** 锁定的 JGit 版本 2018 年发布，存在 CVE-2023-4759（CVSS 8.8）。

**【证据】**
- `pom.xml:51-56`：`org.eclipse.jgit:org.eclipse.jgit:5.1.3.201810200350-r`，注释写明"内网私服已确认可用，Java 8 兼容"
- **CVE-2023-4759**（Arbitrary File Overwrite in Eclipse JGit <= 6.6.0）：恶意构造的 Git 仓库中含符号链接时，JGit 克隆/checkout 可把文件写到工作树之外，在**大小写不敏感文件系统**（Windows、macOS 默认）上可导致 RCE。修复于 6.6.1 / 5.13.3.202401111512-r。（`<已验证>`：联网检索 CVE 数据库确认，版本号与影响范围均匹配）
- **缓解措施未实施**：全库搜索 `symlinks|core\.|StoredConfig` → **0 命中**（`<已验证>`）。官方给出的 workaround 是在 checkout 前设置 `core.symlinks=false`，代码里没有任何相关配置。

**【影响】** 本工具会 `GitCloneService` 自动克隆用户提供的仓库 URL 并 checkout。若克隆了恶意/被投毒的仓库，在 Windows 上可写任意文件。**触发条件**（据 CVE 描述）：受害者需有创建符号链接的权限且 git 配置启用 symlinks —— Windows 默认普通用户可创建符号链接的场景有限，故**实际可利用性中等偏低**（`<推断>`），但 CVSS 8.8 + 目标平台正是 Windows，值得处理。

**【建议】**（不升级 JGit 的前提下即可大幅降险）
1. **立即做**：在 `GitCloneService` 克隆后、checkout 前，通过 JGit 的 `StoredConfig` 显式设置 `core.symlinks = false`：
   ```java
   StoredConfig cfg = git.getRepository().getConfig();
   cfg.setBoolean(ConfigConstants.CONFIG_CORE_SECTION,
                  ConfigConstants.CONFIG_KEY_SYMLINKS, false);
   cfg.save();
   ```
   这正是官方 workaround，对 5.1.3 有效。
2. 在交接文档/启动日志里明确记录该 CVE 与已实施的缓解，避免后续接手者不知情。
3. 中期：推动内网私服代理 JGit 5.13.3（Java 8 兼容的最后一条线），或评估"只保留 5.1.3 但禁用 Git 克隆入口"的降级方案。
4. 另有 CVE-2025-4949（JGit `ManifestParser` XXE），但本工具不使用 `repo` 命令/amazons3 传输，**影响面小**（`<推断>`），QA 可一并备案。

### D-1【P0】调用图构建是 O(N²)：每注册一个方法都要线性扫描全节点表

**【问题】** `CallGraphBuilder` 用**线性扫描**做方法节点去重，而不是哈希索引。

**【证据】**（`<已验证>`）
- `CallGraphBuilder.java:279-286` `indexOfMethod(g, key)`：`for (int i = 0; i < g.getMethods().size(); i++)` 逐个比对 `owner`/`name`/`descriptor` 三个字符串
- `CallGraphBuilder.java:269-277` `ensureMethod()` 每次注册节点都先调 `indexOfMethod`
- `ensureMethod` 的调用点：`CallGraphBuilder.java:161, 173, 201, 213, 224, 235` —— 即**每处理一条调用边都要扫一遍全表**
- `CallGraph.java:64-75` `ensureMethod(GraphMethod)` 也是同样的线性扫描（**但仅测试使用，生产未调用** —— `ExcelReportGeneratorTest.java:56,151`）

**【影响】（量化估算，`<推断>`）**
- 单入口 `MAX_NODES = 50000`（`AnalysisService.java:47`）：注册第 k 个节点需 O(k) 次比较，总计约 `N²/2 = 1.25 × 10⁹` 次三字符串比对。按每次比对 ~50ns 估算，**仅去重就要 60 秒量级**，且这还没算 `resolve()` 与 `expandGraph` 本身。
- 批量场景更糟：`BatchAnalyzeService.java:43` `MAX_NODES_PER_ROOT = 50000` 是**每个入口独立预算**，200 个入口 → 最坏 200 × 50k 节点，且 `bodyCache`/`implCache` 虽跨入口复用，但 `indexOfMethod` 的开销随每个图的规模二次增长。
- 这与"支持十万级节点"的设计目标（交接文档）**严重冲突**。实测中可能因为多数项目的实际调用链远小于 50k 而未被发现（`<推断>`）。

**【建议】**
1. **核心修复（一行改动的量级）**：在 `CallGraphBuilder` 内维护 `Map<MethodKey, Integer> methodIndex`（`MethodKey` 已正确实现 `equals`/`hashCode`，`MethodKey.java:112-120`），把 `indexOfMethod` 从 O(N) 降到 O(1)。`buildGraph`/`buildGraphRoots` 开头清空该 map（与现有 `resetSharedState()` 同位置）。
2. 同理修 D-2 的 `markCycle`（`:254-263`），复用同一索引。
3. 建议 `CallGraph` 自身持有这个索引（而非放在 Builder 里），这样 `AnalysisService.collectGraphStats`（`:529-543`）等下游遍历也能受益，且 `CallGraph.ensureMethod`（`:64`）可一并改成 O(1)。
4. 顺带：`AnalysisService.java:591` `countClassFiles` 用 `Files.walk` + `(int) walk.count()`，对超大项目会有装箱开销，可改 `walkFileTree` 计数（P2）。

### D-3【P1】Phase B 对 jar 依赖：**每个类都重新打开一次 ZipFile**

**【问题】** `MethodCallExtractor` 从 jar 读字节码时，每次调用都 `new ZipFile(...)`。

**【证据】**（`<已验证>`）
- `MethodCallExtractor.java:89-102` `readClassBytes`：`try (ZipFile zip = new ZipFile(location.toFile()))` —— 方法级开闭
- 调用链：`ClassMetadataRegistry.java:184` `MethodCallExtractor.extract(Paths.get(ci.getLocation()), n)` ← `callsOf()` ← `bodyCache.computeIfAbsent`
- 缓存粒度是 **(location, 类名)**（`ClassMetadataRegistry.java:180-182`），因此**每个类只解析一次是对的**，但 `ZipFile` 的打开次数 = 被触及的类数

**【影响】** `ZipFile` 构造要读取并解析整个 central directory（依赖 jar 动辄几 MB~几十 MB，条目数千）。若一次分析触及某 jar 中的 2000 个类，就要解析 2000 次 central directory。`<推断>`：这是依赖 jar 较多时 Phase B 的主要隐藏开销。

**【建议】** 在 `ClassMetadataRegistry` 内维护 `Map<String, ZipFile>`（location → 打开的 ZipFile，惰性打开 + 引用计数），或更稳妥：给 `ProjectLayout` 增加 `close()` 时统一关闭（它已经是 `AutoCloseable`，`AnalysisService.java:88` 就在 try-with-resources 里用）。注意：`AnalysisService.java:404-448` `obtainRegistry` 的 TTL 缓存会持有 `ProjectLayout`，需确保 ZipFile 生命周期与之对齐，避免文件句柄泄漏。

### D-4【P1】"图瘦身了，但 `methodFrequency` 成了新的膨胀源"

**【问题】** 交接文档称图存储"根治了 JSON 膨胀"。图本身确实是瘦的（节点表 + 边表），但**统计区把每个方法的完整调用方列表全量带上了，且不做任何截断**。

**【证据】**（`<已验证>`）
- `AnalysisService.java:52` `DEFAULT_METHOD_TOP_N = Integer.MAX_VALUE` —— 注释写"展示全部去重方法（不截断）"
- `AnalysisService.java:54` `CALLER_CAPTURE_LIMIT = Integer.MAX_VALUE` —— 注释写"不再截断，完整采集供单方法导出使用"
- `AnalysisService.java:529-543` `collectGraphStats`：对每条边 `a.callers.add(new CallerInfo(caller.toKey(), edge.getLine()))`
- `AnalysisService.java:558-570` `toFrequency`：`mc.setCaller(ci.caller.getIdentifier())` —— **每个调用方都序列化成完整全限定标识字符串**（如 `com.foo.Bar#pay(String, int)`）

**【影响】（量化，`<推断>`）** 设图有 E 条边，则 `methodFrequency` 里含 **E 个 `MethodCaller` 对象**，每个带一个 ~40-80 字节的标识字符串 + 行号。加上 JSON 的 key 重复（`"caller"` / `"line"` 每个对象都写一遍），**频次区的体积约为边表本身的 2-4 倍**。而这份数据会：① 作为 `AnalysisResult` 的一部分经 HTTP 返回给前端；② `AnalysisService.java:344` 全量写入每入口的 JSON 缓存文件（带 `INDENT_OUTPUT` 缩进，`AnalysisCacheService.java:42` —— **缩进又放大约 30-50%**）。

**【建议】**
1. `MethodCaller.caller` 改为存 **methodId（int）** 而非标识字符串，前端按 `graph.methods[id]` 解析展示。这一项可把频次区体积压掉 60%+，且与"图存储"的设计哲学一致。
2. `AnalysisCacheService.java:42` 关闭 `INDENT_OUTPUT`（缓存文件是机器读的，不需要人类可读；`save` 用它只是为了方便调试，可改为按 `logging.level` 或系统属性开关）。
3. 调用方列表改为**分页/按需**：接口默认只返回 `callCount`，展开某方法时再走 `/api/method-callers`（修好 A-1 之后）单独拉。

### D-5【P1】`NoiseRuleService.matches()` 每次调用都 `Pattern.compile()`

**【问题】** 正则在热路径上被反复编译。

**【证据】**（`<已验证>`）
- `NoiseRuleService.java:549-557` `matches(regex, input)`：`return Pattern.compile(regex).matcher(input).find();`
- 调用点：`:476`、`:478`（`isNoiseOnRules` 内，每个规则 1-2 次）、`:501`、`:503`（`getMatchedRuleOnRules`）
- 热路径：`ExcelReportGenerator.java:76`（单入口导出，对**每个** `MethodFrequency` 调一次）、`:116`（项目级导出，对聚合后的**每个**方法调一次）、`:256`（每个根方法）

**【影响】** 设 10000 个方法 × 20 条启用规则 × 2 个 pattern = **40 万次 `Pattern.compile`**。`Pattern.compile` 涉及语法解析与状态机构建，单次 ~1-10μs，总计 0.4-4 秒纯编译开销（`<推断>`）。而且规则内容在运行期是稳定的，完全是浪费。

**【建议】** 在 `NoiseRuleService` 内维护 `Map<String, Pattern> patternCache`（Guava/Caffeine 或 `ConcurrentHashMap` + 上限淘汰），`matches()` 走 `patternCache.computeIfAbsent(regex, Pattern::compile)`。规则变更（`save`/`reset`/`saveProjectRules`）时清空缓存。这是**改动最小、收益最确定**的一项。

### D-8【P2】`Files.walk` 使用 20+ 处，部分场景代价过高

**【证据】**（`<已验证>`，全库统计 24 处 `Files.walk`/`Files.list`）

### D-9【缓存策略可靠性专项评估】

针对主理人问的"缓存策略是否可靠，失效判定是否可能误判"：

**结论：不可靠 —— 不是"可能误判"，而是"根本不判定"。**

- **持久缓存（`.callgraph/cache/*.json`）**：见 C-1。文件名 = f(入口, maxDepth, maxNodes, freqFilter)，**不含任何项目状态**。`projectFingerprint()` 存在但零调用。→ **必然误判：改了代码仍返回旧结果**。
- **内存 `resultCache`（`AnalysisCacheService.java:290-326`）**：用 `mtime + size` 双因子判定（`:309`），**可靠**。容量 12、单文件上限 8MB（`:275-276`），超限不缓存（`:315`）—— 设计合理。`LinkedHashMap(accessOrder=true)` + `synchronized` 保护（`:307,:316`）—— 正确。唯一瑕疵：`getLastModifiedTime` 在部分文件系统上精度是秒级，同一秒内"改文件且大小不变"会被漏判（`<推断>`，Windows NTFS 时间戳精度约 100ns，实际风险低）。
- **注册表 `CacheSlot`（`AnalysisService.java:56-81`）**：单槽 + 5 分钟 TTL（`:48`）+ `synchronized`（`:404-408`）。**单槽是硬伤**：交替分析两个项目会持续互相驱逐、每次重建注册表（重建代价是解析全部 class 头）。内网单人使用可接受（`<推断>`），但两人共用就会退化成"每次都全量重建"。
- **`NoiseRuleService.projectRuleCache`（`:92-108`）**：`mtime + size` + 2 秒最小重查间隔（`:95`）—— **可靠**，且注释（`:89-91`）明确说明了为什么加缓存，很好。
- **`ProjectsController.statusCache`（`:86-106`）**：20 秒 TTL + 显式失效（`:108-110`）—— **可靠**。

**建议**：① 优先修 C-1（持久缓存）；② 把 `AnalysisService` 的单槽 `CacheSlot` 改为 `LinkedHashMap` 小容量 LRU（2-3 槽）即可覆盖 90% 的来回切换场景，改动量极小；③ 内存 `resultCache` 的 12 条/8MB 上限是针对当前单机单人设计的，若并发上升需重新评估。

### D 维度健康度评分：**48 / 100**

**扣分理由**：工程里**已经做对了不少性能优化** —— 两阶段字节码解析（Phase A `SKIP_CODE`）、图存储替代树存储、`SXSSFWorkbook` 流式 Excel（`ExcelReportGenerator.java:62,102`）、惰性邻接表（`CallGraph.java:41-48`）、噪声规则缓存（`NoiseRuleService.java:89-108`）、批量分析"按入口单文件落盘 + 只留轻量索引"以免聚合到 GB 级（`BatchAnalyzeService.java:29-34`）—— 这些说明作者有明确的性能意识。但 **D-1/D-2 的 O(N²) 图构建是一个足以让"十万级节点"目标彻底落空的单点缺陷**，且修复成本极低（加个 HashMap 索引）。D-4（频次区膨胀抵消了图瘦身的收益）和 D-5（热路径反复编译正则，而前端已优化后端没跟上）同理。这三项修复后本维度可到 75+。

| **A. 代码架构** | **62** | 分层正确、SPI 用得好、路径收口到位；但 web 层越界、异常体系覆盖不足、单例可变状态埋雷 |

> 综合分按 A 30% / B 25% / C 25% / D 20% 加权：62×0.3 + 45×0.25 + 55×0.25 + 48×0.2 ≈ **53**

### 哪些地方能放心改

- **`engine/` 包整体**：不依赖 Spring，纯 POJO + ASM，`MethodKey`/`CallGraph`/`GraphEdge` 都是干净的值对象，**测试覆盖也最好**（engine 层 7 个测试类）。加新的入口探测器、改调用图语义，风险最低。
- **`EntryPointDetector` SPI**：接口只有 3 个方法（`type()`/`label()`/`detect()`），加一个自定义探测器（如 XXL-Job、RocketMQ 消费者）只需新建一个 `@Component` 类，无需改动任何既有代码。这是**最能快速交付业务价值**的扩展点。
- **噪声规则 / 扫描策略的双层配置**：`NoiseRuleService` 与 `ScanStrategyService` 结构同构、Javadoc 完整、有独立的 Controller，改起来有清晰边界。
- **`JobLogBuffer`**（新代码）：34 行、`synchronized`、职责单一，是本次评审中质量最高的新增代码，可作为后续重构的**代码风格样板**。

### 哪些地方一碰就出事

1. **`AnalysisService.lastResult` / `lastResultProjectPath`**（`:59-61`）—— 跨请求共享可变状态，改动前先理解 Excel 导出（`AnalysisController.java:276-309`）对它的依赖链，否则会出现"导出到别人的结果"。
2. **`app.js` 的 `escapeHtml`**（`3541` vs `3925`）—— 同名两份、语义不同、后者覆盖前者。改任何一处 innerHTML 渲染前必须确认生效的是哪一份。
3. **缓存文件名规则**（`AnalysisCacheService.cacheName()` `:343-350`）—— 它与 `save`/`load`/`fileNameOf`/`pruneBatchEntries` 四处强耦合（后者还靠 `isPerEntryFile` 的"以 8 位 hex 结尾"约定来识别），改文件名格式会同时影响批量分析的旧文件清理逻辑。
